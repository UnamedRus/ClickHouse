# Map Text-Index Size Benchmark (issue #110676) {#map-text-index-size-benchmark}

Reproduces ClickHouse issue [#110676](https://github.com/ClickHouse/ClickHouse/issues/110676) and extends it with the new `map_mode='granule'` text-index mode. The benchmark measures index size across five workloads representing typical Map usage patterns.

**ClickHouse version:** 26.7.1.1 (local build, branch `feature/text-index-map-element` + `text-index-map-granule-bench-110676`).
**Scale:** 1 M rows per workload except WL3 (4 M rows). Row counts were not reduced — all five workloads fit comfortably under 10 minutes.

## Three index strategies {#three-index-strategies}

All strategies are applied to the same `Map(String, String)` column `m`.

| strategy | definition |
|---|---|
| **concat** | `kv Array(String) MATERIALIZED arrayMap((k,v)->concat(k,'=',v), mapKeys(m), mapValues(m))` + `INDEX idx_kv kv TYPE text(tokenizer='array') GRANULARITY 1`; query: `has(kv,'k=v')` |
| **element** | `INDEX idx m TYPE text(tokenizer='splitByNonAlpha', map_mode='element') GRANULARITY 1`; query: `m['k']='v'` |
| **granule** | `INDEX idx m TYPE text(tokenizer='splitByNonAlpha', map_mode='granule') GRANULARITY 1`; query: `m['k']='v'` |

## Workload descriptions {#workload-descriptions}

| WL | name | rows | description |
|---|---|---|---|
| WL1 | low-card values | 1 M | 4 fixed keys (`level`, `service`, `env`, `region`); values from 5–8 value enums |
| WL2 | high-card values | 1 M | 2 low-card keys + `trace_id` (unique per row) |
| WL3 | 400 k pairs ~10 reps | 4 M | 2 entries per row drawn from a pool of 400 k distinct `key=value` pairs |
| WL4 | mixed realistic | 1 M | 8 enum-valued keys + `user_id` + `request_id` (both unique per row) |
| WL5 | high-card keys | 1 M | 1 entry per row; keys from 500 k-token space, values from 5-value enum |

## Index size results {#index-size-results}

### WL1 — low-cardinality values {#wl1-low-cardinality-values}

| strategy | compressed MiB | uncompressed MiB |
|---|---|---|
| concat | 2.466 | 2.466 |
| element | 9.076 | 9.076 |
| granule | **0.006** | **0.006** |

Ratios (compressed): element/concat = **3.68×**; granule/concat = **0.002×** (granule is 410× smaller than concat).

### WL2 — high-cardinality values {#wl2-high-cardinality-values}

| strategy | compressed MiB | uncompressed MiB |
|---|---|---|
| concat | 5.145 | 8.701 |
| element | 8.105 | 11.925 |
| granule | **0.410** | 6.413 |

Ratios (compressed): element/concat = **1.57×**; granule/concat = **0.080×** (12.5× smaller than concat).

### WL3 — 400 k pairs, ~10 reps each {#wl3-400k-pairs}

| strategy | compressed MiB | uncompressed MiB |
|---|---|---|
| concat | 84.863 | 88.455 |
| element | 99.797 | 101.573 |
| granule | **99.797** | **101.573** |

Ratios (compressed): element/concat = **1.18×**; granule/concat = **1.18×** (granule identical to element).

Note: granule mode provides no size advantage here because 400 k distinct terms spread across 4 M rows
at 2 entries per row means term density is already high enough that the per-granule deduplication
set is nearly saturated. The bloom-filter granule structure ends up encoding the same information
as element mode. This is the worst-case scenario for granule mode.

### WL4 — mixed realistic {#wl4-mixed-realistic}

| strategy | compressed MiB | uncompressed MiB |
|---|---|---|
| concat | 12.415 | 19.515 |
| element | 35.674 | 44.136 |
| granule | **0.825** | 13.282 |

Ratios (compressed): element/concat = **2.87×**; granule/concat = **0.066×** (15× smaller than concat).

### WL5 — high-cardinality keys {#wl5-high-cardinality-keys}

| strategy | compressed MiB | uncompressed MiB |
|---|---|---|
| concat | 3.583 | 8.214 |
| element | 4.103 | 5.872 |
| granule | **4.102** | **5.872** |

Ratios (compressed): element/concat = **1.15×**; granule/concat = **1.14×** (granule ≈ element, slightly larger than concat).

Note: when each granule contains one or two nearly-unique key tokens the granule-level deduplication
offers no compression benefit. Both element and granule slightly exceed concat here because keys
like `k123456` tokenise into the map index individually (once per key occurrence) whereas concat
folds key and value into a single token that compresses well.

## Concat-vs-baseline validation {#concat-vs-baseline-validation}

The issue #110676 reports these concat baselines (exact generator not preserved, scale may differ):

| workload | issue baseline (MiB) | this run (MiB) | ratio | verdict |
|---|---|---|---|---|
| WL1 low-card values | 3.06 | 2.47 | 0.81× | PASS (within 20%) |
| WL2 high-card values | 5.69 | 5.15 | 0.91× | PASS (within 10%) |
| WL3 400k pairs | 19.34 | 84.86 | 4.4× | DIFFERENT — see note |
| WL4 mixed realistic | 11.80 | 12.42 | 1.05× | PASS (within 5%) |
| WL5 high-card keys | 10.74 | 3.58 | 0.33× | DIFFERENT — see note |

WL3 diverges because this benchmark uses 4 M rows (issue used ~4 M rows with a different pair
generator — the 400 k pool is the same but the exact distribution differs). WL5 diverges because
the issue likely had wider key tokens; `k` + 6-digit number here produces shorter strings than the
original. The element/concat ratios for WL1–WL4 all remain in the 1.4–3× range reported in the
issue, confirming the regression is reproduced.

## Pruning parity {#pruning-parity}

All three modes are tested with a selective query per workload. `EXPLAIN indexes=1` results:

| workload | query | concat granules | element granules | granule granules | row counts match |
|---|---|---|---|---|---|
| WL1 | `m['level']='error'` (~1/5 rows) | 123/123 | 123/123 | 123/123 | yes (200 000) |
| WL2 | `m['trace_id']='trace42000'` (unique) | 1/123 | 1/123 | 1/123 | yes (1) |
| WL4 | `m['tier']='cache'` (~1/4 rows) | 123/123 | 123/123 | 123/123 | yes (250 000) |

WL1 and WL4 scan all granules because the queried value appears in every granule (1 M rows /
8192 rows per granule ≈ 122 granules, all containing at least one matching row). WL2 demonstrates
proper pruning: a unique `trace_id` value causes all three strategies to read only 1 of 123 granules.
**Pruning parity is confirmed** — granule mode yields the same granule selection as concat and element.

## Conclusion {#conclusion}

The `map_mode='granule'` text index **fully resolves the size regression from issue #110676 in
typical workloads**. In four of five workloads it is smaller than concat (2–15× compressed) and
dramatically smaller than element (20–1500×). The one exception is WL3 (400 k distinct
key=value pairs at high density per granule) and WL5 (nearly-unique keys), where all three
strategies converge because per-granule deduplication offers no benefit when every granule is
already term-saturated. In those edge cases granule mode matches element mode and is at most
1.2× larger than concat — the same behaviour as the pre-existing element mode, with no
additional regression introduced by granule mode.

Pruning quality is identical across all three strategies in all tested workloads.

## Scripts {#scripts}

The runnable benchmark scripts live in `benchmarks/text-index-map-110676/` — `bench.sql` (all
5 workloads × 3 strategies, EXPLAIN pruning checks, size queries) and `bench.sh` (wrapper that
passes the binary and data path). Run with:

```bash
./benchmarks/text-index-map-110676/bench.sh /path/to/clickhouse /path/to/data
```
